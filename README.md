# Requiem

---

## 프로젝트 개요

Requiem은 개인 창작물을 기록하고 공유하기 위한 웹 애플리케이션입니다. 캐릭터 프로필, 게시글, 이미지 갤러리와 방명록을 하나의 공간으로 구성했습니다.

외주 프로젝트로 기획·디자인·개발·배포를 단독으로 진행했습니다. 창작물 관리 기능과 함께 단계별 인트로, 프로필 목차, 배경음악 등 사이트의 분위기를 표현하는 인터랙션을 구현했습니다.

- 개발 형태: Spring Boot 기반 웹 애플리케이션
- 개발 인원: 1인 — 외주 단독 개발
- 개발 기간: 6일
- 담당 범위: 기획, 디자인, 프론트엔드·백엔드 구현, 데이터베이스 구성 및 배포
- 배포 환경: 가비아 컨테이너 호스팅

[배포 주소](https://infected-requiem.com/)

## 구조 및 설계

### MVC와 REST API의 병행

Controller에서 초기 데이터와 화면을 전달하고, Service와 MyBatis Mapper를 통해 데이터베이스에 접근하도록 구성했습니다. `repository` 패키지에는 MyBatis Mapper 인터페이스를 배치하고, SQL은 Mapper XML에서 관리했습니다.

프로필과 게시글 상세는 Model에 데이터를 담아 Thymeleaf로 렌더링했습니다. 게시판·갤러리·방명록 목록과 회원 인증 등의 기능은 REST API와 Fetch API로 처리했습니다.

프로필과 게시글의 작성·수정은 일반 폼 제출과 저장 후 리다이렉트 방식으로 구성했습니다.

### 공통 UI와 목록 처리

헤더·푸터·상하단 이동 버튼·토스트·페이지 버튼 영역을 Thymeleaf fragment로 분리했습니다. 에디터 초기화와 제거, 이미지 업로드 설정도 공통 JavaScript 유틸리티로 구성했습니다.

게시판·갤러리·방명록은 전체 개수 조회와 페이지별 목록 조회를 분리했습니다. 서버에서는 `LIMIT`과 `OFFSET`으로 필요한 범위만 조회하고, 프론트엔드에서는 공통 페이지네이션 모듈로 현재 페이지와 버튼 표시를 관리했습니다.

공통 CSS에는 모바일 화면을 위한 글자 크기와 헤더·푸터 배치 조정을 적용했습니다.

## 주요 기능

## 구현

### 단계별 인터랙티브 인트로

인트로의 대사를 데이터 배열로 분리하고, 현재 단계와 대사 인덱스, 중복 실행 방지 상태를 관리했습니다. 사용자 클릭과 타이머에 따라 대사·버튼·오버레이를 순차적으로 변경하도록 구성했습니다.

단계에 따라 팝업을 생성하거나 제거하고, 배경과 BGM을 전환했습니다. 팝업 복제와 글리치, 화면 플래시 등의 연출을 조합하고 마지막 대사 이후 메인 화면으로 이동하도록 구현했습니다.

화면 크기에 따라 팝업의 너비와 배치 범위를 조정해 모바일에서도 연출을 표시하도록 구성했습니다.

### 프로필 블록 편집과 목차 자동 생성

프로필 편집 화면에서는 세 단계의 제목과 TinyMCE 본문 블록을 추가·삭제하고 순서를 변경할 수 있도록 구현했습니다.

본문 블록을 이동할 때는 에디터 내용을 보관한 뒤 인스턴스를 제거하고, 이동한 위치에서 다시 초기화해 내용을 복원했습니다. DOM 이동 과정에서 에디터 상태와 입력 내용이 유지되도록 처리했습니다.

저장 시에는 화면의 블록 순서대로 제목 번호와 본문 HTML을 조립해 서버에 전달했습니다. 다시 편집할 때는 저장된 HTML을 `DOMParser`로 읽어 제목과 본문 블록을 복원했습니다.

메인 화면에서는 프로필의 제목 요소를 읽어 목차를 자동으로 생성했습니다. 목차에서 해당 본문으로 이동하거나, 본문 제목에서 목차로 돌아오는 부드러운 스크롤을 구현했습니다.

### JWT 쿠키 기반 인증

회원가입 시 비밀번호를 BCrypt로 해싱해 저장하고, 로그인에서는 데이터베이스의 회원 정보와 비밀번호를 확인했습니다. ID 중복 확인 API를 제공하고, 입력 오류와 로그인 실패는 토스트로 안내했습니다.

로그인에 성공하면 사용자 ID와 역할을 담은 JWT를 발급해 HttpOnly 쿠키로 전달했습니다. 요청마다 필터에서 쿠키의 토큰을 검증하고 Spring Security 인증 정보를 구성하도록 구현했습니다.

인증에는 `STATELESS` 정책을 적용했습니다. 프로필 수정, 게시글 관리, 카테고리 관리와 갤러리 업로드·삭제 경로에는 관리자 Role을 확인하는 접근 규칙을 설정했습니다.

로그아웃은 인증 쿠키의 유효기간을 0으로 설정해 브라우저에서 제거하는 방식으로 처리했습니다.

### 카테고리 기반 게시판

게시판 목록은 선택한 카테고리를 조회 조건으로 전달하고, 전체 개수와 페이지별 게시글을 API로 불러오도록 구성했습니다. 서버에서는 한 페이지에 열 개씩 조회했습니다.

게시글 작성과 수정은 하나의 Thymeleaf 폼을 재사용했습니다. TinyMCE로 본문을 편집하고, 서버에서는 카테고리·제목·본문의 필수값을 확인한 뒤 저장했습니다. 존재하지 않는 게시글의 조회·수정·삭제에는 오류 안내와 리다이렉트를 적용했습니다.

카테고리 등록 시에는 공백과 중복 이름을 검사했습니다. 기본 ‘공지’ 카테고리는 Service와 SQL 양쪽에서 삭제를 제한했습니다.

### 갤러리와 이미지 처리

갤러리는 이미지 파일을 먼저 업로드한 뒤 반환된 URL과 작품명·작가 정보를 별도 요청으로 저장하는 구조로 구현했습니다. 목록은 서버에서 열 개씩 조회하고, 이미지를 클릭하면 확대해서 볼 수 있도록 구성했습니다.

공통 이미지 업로드 API에서는 빈 파일, 최대 10MB 용량, 허용 확장자와 요청 MIME 타입을 검사했습니다. 파일명은 UUID로 생성하고, 업로드 경로는 설정값을 기준으로 구성했습니다.

GIF는 원본을 유지하고, 그 외 이미지는 디코딩 후 해상도와 픽셀 수를 검사했습니다. 너비가 1,000px을 초과하면 Thumbnailator로 비율을 유지하며 축소했습니다.

갤러리 삭제 시에는 데이터베이스의 이미지 정보를 삭제한 뒤 연결된 서버 파일도 삭제하도록 처리했습니다. 파일 삭제 대상이 업로드 디렉터리 내부에 있는지 확인하는 경로 검사도 적용했습니다.

### 방명록과 사용자 차단

방명록은 로그인한 사용자만 작성할 수 있도록 구성했습니다. 작성자 ID는 클라이언트 입력 대신 서버 인증 정보에서 가져오고, 등록 전에 해당 사용자의 방명록 작성 차단 여부를 확인했습니다.

목록은 서버에서 다섯 개씩 조회했습니다. 화면에서는 비밀글 여부와 로그인 사용자 정보를 기준으로 본문 표시를 분기하고, 관리자에게 답변·답변 삭제·차단 버튼을 제공했습니다.

답변은 기존 답변이 없는 방명록에만 등록하도록 SQL 조건을 두었습니다. 사용자 차단 시에는 차단 상태 변경과 해당 작성자의 방명록 전체 삭제를 하나의 트랜잭션으로 처리했습니다.

비밀글 응답과 방명록 관리 요청의 서버 권한 검증에는 보완이 필요한 부분이 남아 있습니다.

### 공통 페이지네이션과 BGM 상태 복원

페이지네이션 모듈은 전체 개수 조회, 페이지 조회, 목록 렌더링 함수를 옵션으로 받아 재사용하도록 구성했습니다. 현재 페이지 주변의 번호와 이전·다음 버튼을 표시하고, 데이터 변경 후에는 전체 개수와 목록을 다시 조회하도록 구현했습니다.

공통 토스트는 타이머와 닫힘 상태를 관리해 연속된 알림을 처리했습니다.

BGM 플레이어는 재생·정지, 진행 상태 표시와 재생 위치 이동을 제공했습니다. 재생 위치와 재생 여부를 `sessionStorage`에 저장하고 페이지 이동 후 복원했습니다. 브라우저가 자동 재생을 허용하지 않는 경우에는 사용자 클릭이나 터치 이후 재개하도록 처리했습니다.

## 기술적 고민 및 개선점

### 방명록의 서버 권한과 비밀글 응답

방명록은 화면에서 작성자와 관리자 여부에 따라 비밀글 본문을 숨기지만, 목록 API의 응답에는 본문과 답변이 포함되는 한계가 있습니다. 서버에서 열람 권한을 확인하고, 권한이 없는 사용자에게는 비공개 내용을 반환하지 않도록 개선할 필요가 있습니다.

답변과 차단 버튼은 관리자에게만 표시하지만, 관련 API는 현재 로그인 여부만 확인합니다. 화면의 역할 분기와 서버 접근 규칙을 일치시켜 관리 작업에 관리자 권한을 명시적으로 요구하도록 보완하고자 합니다.

### HTML 콘텐츠 검증

프로필과 게시글은 에디터에서 작성한 HTML을 저장하고 그대로 렌더링하는 구조입니다. 필수값 검사는 구현했지만, 서버에서 허용할 HTML 태그와 속성을 제한하는 처리는 보완이 필요합니다.

HttpOnly 쿠키 적용과 콘텐츠 검증의 역할을 구분하고, 저장·출력 과정에서 HTML과 URL을 검증하는 기준을 정리하고자 합니다.

### 이미지 파일과 메타데이터의 일관성

이미지 업로드와 갤러리 정보 저장이 별도 요청이어서 파일 저장 이후 메타데이터 등록에 실패하면 사용되지 않는 파일이 남을 수 있습니다. 삭제 과정도 데이터베이스를 먼저 갱신하고 파일 삭제 오류를 무시하므로 두 저장소의 상태가 달라질 수 있습니다.

후속 개선에서는 등록 실패 시 업로드 파일을 정리하고, 파일 삭제 실패를 기록해 다시 처리할 수 있도록 보완하고자 합니다.
